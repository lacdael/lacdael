WAV looper

📅 24/08/2028, 01:00:00

To gain hands-on experience of working with cross-task data streams in an RTOS environment, audio playback from an SD card is a good place to start. You can hear immediately when there is an issue with the handling of the stream.

The aim was to make a prototype device with a touch screen user interface to control the behaviour of the device, an SD card to read WAV file audio data from, and an I2S interface to send audio data out of.

Watch the Video

WAV files

WAV files are ideal for an embedded environment, as the file format contains uncompressed pulse-code modulation data, which can directly be sent to an audio chip. This means there is no overhead for decompression and decoding. The header of the WAV file contains all the relevant data needed to process the data.

  • Sample rate
  • Number of audio channels
  • Bits per sample
  • Audio format
  • Location and size of the audio data

Rendering the WAV file

A selected region of the WAV file was rendered in the UI. This was done by using the header data of the audio file to calculate the bars that needed to be rendered to represent a section of the audio file.

RTOS

The system was made up of 3 main tasks:

  • SD card task reading data from the SPI interface connected to the SD card.
  • I2S audio task sending audio data out to an audio chip.
  • UI task with an SPI connection to a display and an SPI connection to a touch screen controller.

The basic flow of audio data is from the SD card into audio buffers. The audio buffers are then handed off to the audio task via queue messages, and the audio buffer data is sent out via I2S.

The SD card and I2S interface don't necessarily operate at the same rate, and so a reasonable buffer size is needed to enable the producer and consumer tasks to work together. If I2S drains the audio buffer data faster than the SD task can provide new audio data, then the audio stream will be interrupted and the result will be audible.

Audio Buffers

Two audio buffers were created. The SD card producer task filled one buffer, then used a queue message to hand off ownership of the buffer to the audio I2S task. The SD card task then started filling the second buffer. When the I2S audio task was finished with the first buffer, ownership of the two buffers was swapped via queue message signalling. This then continued.

An alternative method would be to have a shared ring buffer, and then use queue messages to signal the head and tail positions in the ring buffer once a batch of processing has completed.
